# ByteSavor 答辩 QA 文稿

用途：老师/同学提问时快速回答。回答建议控制在 20-40 秒，先说结论，再补工程证据。

## 1. 项目定位类

### Q1：你们这个项目和普通菜谱 App 有什么区别？

**答：**

普通菜谱 App 主要解决“搜菜谱”。ByteSavor 解决的是从看到食物到执行饮食决策的完整链路。用户拍照识别食材以后，系统会结合目标、偏好、营养缺口推荐菜谱，再生成清单或用餐计划。用户在首页点击“完成这一餐”以后，营养进入长期记录，同时弹出评分和原因输入，写入偏好记忆，下一轮推荐会受到影响。所以它不是一次性搜索，而是一个持续学习的饮食 Agent。

### Q2：为什么叫“全场景饮食全链路”？

**答：**

“全场景”指家庭做饭、健康管理、买菜、探店、备餐采购和长期个性化这几类场景都覆盖了；“全链路”指 B-Y-T-E：B 感知、Y 决策、T 执行、E 反馈。从图片或文字输入开始，到推荐、清单、加入计划、完成用餐、营养记录和偏好学习结束。

### Q2.5：注册和登录是真实的吗？不同账号的数据会隔离吗？

**答：**

是真实落库的。演示版注册时用微信ID/OpenID 作为账号标识，后端会写入 MySQL 的 `users` 表，并创建对应的 `profiles`。登录时后端按 OpenID 查库，成功后签发 JWT。后续库存、用餐记录、营养汇总、偏好记忆都按 `user_id` 写入和查询，所以换一个新账号会是新的画像和新的历史数据，不会沿用上一个账号的记录。

### Q3：是不是功能太多，主线不清楚？

**答：**

我们不是按功能堆按钮，而是按角色组织。每个角色有独立入口，便于测试和演示；Agent 是统一入口，负责把这些工具按用户任务串起来。这样既保证功能可单独验证，也能保留完整闭环。

## 2. Agent 类

### Q4：你们的 Agent 具体体现在哪里？不是一个聊天框吗？

**答：**

不是单纯聊天框。我们的 Agent 有三个层次：第一，解析自然语言和图片输入，抽取食材、目标、时间限制等结构化意图；第二，根据任务调用工具，比如 sense、decision、task、nutrition、quality、guide；第三，把结果和反馈写回状态和长期记忆。每次调用会返回 trace_id、events、stages、degraded 等信息，所以它是可追踪的工具编排器。

### Q5：stage 状态、耗时和降级信息具体怎么实现？

**答：**

Agent runtime 在每次工具调用前写入 `tool_start`，调用结束后写入 `tool_result`。`tool_result` 里包含 `tool`、`status`、`latency_ms`、`summary`；如果失败，会额外记录 `error_code` 和错误摘要。路由层再把这些 events 整理成 stages，给前端展示。只要 state 里有 errors，总结果的 `degraded` 就会是 true。

### Q6：如果 VLM 或 LLM 慢了，现场怎么兜底？

**答：**

有两层兜底。第一是 Agent 级兜底，某个工具失败时不会伪造 mock 结果，而是记录 error_code、latency 和 degraded，尽量返回已完成的部分结果。第二是业务级兜底，比如推荐硬过滤没有结果时，会 fallback 到相近菜谱，并在结果里标记 fallback。现场演示如果外部模型慢，我们可以切换到 demo_tests 图片、角色页面或 Swagger 接口，同时解释具体是哪一层降级。

### Q7：Agent 会保留上下文吗？

**答：**

会。Agent 使用 conversation_id 保存会话状态。如果第一轮推荐了菜谱，第二轮用户说“把刚才的菜生成购物清单”，系统可以复用上一轮的 recipes，不需要重新推荐。测试里也覆盖了这个多轮上下文。

## 3. 推荐算法类

### Q8：推荐算法是怎么打分的？

**答：**

推荐不是简单返回数据库前几条。它先按时间等条件做硬过滤，再做软排序。核心分数由食材匹配、标签/目标匹配和偏好匹配组成。食材匹配现在更重视用户明确说出的核心食材覆盖，比如“牛肉南瓜减脂30分钟”会优先推荐同时覆盖牛肉和南瓜的菜，而不是只因为低碳高蛋白就首推芹菜牛肉。偏好匹配来自用户画像和 preference memories，用户不喜欢的标签或食材会降权。

### Q9：为什么要做 fallback 推荐？

**答：**

因为真实输入经常很苛刻，比如用户只有两个食材，又要求 10 分钟、低碳、高蛋白。如果完全没有满足条件的菜谱，直接返回空体验很差。我们会放宽条件返回相近菜谱，并标记 fallback，让前端提示“未找到完全匹配，为你推荐相近方案”。

### Q10：偏好数据库如何影响推荐？

**答：**

用户完成一餐后，前端会弹出评分，并继续让用户写原因，比如“喜欢清淡少油、高蛋白”或“太油腻”。后端会用 LLM 或本地规则解析成 liked_tags、liked_ingredients、avoid_tags、avoid_ingredients，写入 `preference_memories`。下次推荐时，decision 路由会读取这些 signals，把 liked 加入用户偏好，把 avoid 放入降权约束。

## 4. 营养与数据类

### Q11：为什么识别之后不能直接计入摄入？

**答：**

因为拍到食物不代表用户真的吃了。比如拍冰箱食材只是库存，拍菜单也只是识别，导出清单也只是准备动作。我们把识别、推荐、清单、加入用餐计划和完成这一餐分开，只有用户在首页用餐计划里点击“完成”，才写入 completed 的 MealRecord，健康看板也只统计 completed 记录。

### Q12：营养数据准确吗？

**答：**

我们定位是健康建议级估算，不是医学诊断。系统会根据识别分量、食材营养表和用户个人目标估算热量、蛋白、碳水、脂肪、纤维、维 C 和铁等。用户可以在识别后修订、删除，如果已计入后发现错误，也能在健康看板删除记录。

### Q13：每日营养目标怎么计算？

**答：**

用户可以自定义目标；如果不自定义，系统会根据性别、年龄、身高、体重、每周运动次数和目标类型计算。基础公式类似 BMR + 活动系数，再根据减脂、均衡、增肌调整热量和蛋白质目标。

### Q14：代码行数为什么这么多？

**答：**

我们会分开讲。核心手写代码约 1.23 万行，其中后端 Python 约 3,636 行，前端 Vue/JS 约 7,935 行，测试约 724 行。全工程约 15 万行，主要是因为菜谱数据 `recipes.json` 有 138,252 行，这部分体现数据规模，不是业务代码凑数。

## 5. 工程与测试类

### Q15：你们怎么证明功能不是只在演示路径上能跑？

**答：**

我们做了角色化测试。家庭做饭用户对应识别、校正、推荐；健康用户对应加入计划、完成一餐、删除记录、营养汇总；买菜用户对应品质鉴定；探店用户对应菜品故事和吃法；长期个性化用户对应完成一餐后的评分和偏好记忆。最新验证里，Agent/运行时相关 17 个测试通过，带数据库的核心链路 16 个测试通过，两个前端 H5 构建也通过。

### Q16：软件规模是否满足课程要求？

**答：**

满足。要求是用例超过 3 个、源文件超过 5 个、代码超过 500 行。我们有 11 个自动化测试文件，主要源文件接近 100 个，核心手写代码约 1.23 万行，全工程含菜谱数据约 15 万行。

### Q17：如果模型返回格式不标准怎么办？

**答：**

后端不会直接相信模型文本。对于 VLM/LLM 输出，会做 JSON 提取、字段规范化和本地 fallback。比如偏好解析时，如果 LLM 没返回标准 JSON，会退回本地规则，把“高蛋白、清淡、油腻”等词转成统一标签。

### Q18：为什么不用一个大接口覆盖所有功能？

**答：**

因为课程项目更需要可测试和可解释。我们把 nutrition、quality、guide、sense、decision、task 分成独立接口，每个角色页面能单独跑通；Agent 再作为统一入口调用它们。这样比一个黑盒大接口更稳定，也更容易定位问题。

## 6. 安全与风险类

### Q19：你们怎么处理 mock 数据风险？

**答：**

我们不把 mock 当成模型结果。如果外部模型不可用，后端会返回错误、空结果或 degraded，而不是编造识别结果。这样虽然用户会看到失败提示，但数据不会污染后续推荐和营养记录。

### Q20：OpenID 直传安全吗？

**答：**

这是课程演示环境的简化。当前代码里也标注了安全说明：生产环境应该由前端传微信 code，后端调用 code2session 换取 openid，不能让客户端直接伪造 openid。我们答辩时会明确这是演示版账号标识，不把它包装成生产级微信登录。

### Q20.5：有没有注册密码？密码怎么保存？

**答：**

当前演示版没有密码字段，注册页输入的是微信ID/OpenID，不会把明文密码保存进数据库。如果后续做普通账号密码登录，应该只保存 bcrypt 或 argon2 这类哈希后的密码，并加登录限流和错误次数控制；不能保存明文密码。如果做微信小程序登录，则更推荐走后端 `code2session`，不需要用户手输密码。

### Q21：JWT 和密钥怎么处理？

**答：**

后端启动会检查 JWT_SECRET，Docker 配置也要求显式设置密钥。演示环境使用测试密钥，生产环境需要换成高强度随机密钥。

## 7. 现场演示类

### Q22：如果现场网络不好怎么办？

**答：**

我们准备了三层兜底。第一，使用本地已有的 demo_tests 图片，避免临时找素材。第二，如果 VLM/LLM 慢，切到独立角色页面或已跑通接口。第三，如果前端现场异常，直接用 Swagger 或 pytest/build 结果证明核心后端流程是通的。

### Q23：你们最想让老师看到的演示主线是什么？

**答：**

主线是：设置用户画像 -> 拍照识别 -> 校正食材 -> 生成清单和营养占比 -> 加入某个餐时计划 -> 首页完成这一餐 -> 健康看板更新 -> 弹出评分和原因 -> 偏好记忆 -> 下次推荐更个性化。这条线最能体现 B-Y-T-E 闭环。

### Q24：这个系统还有哪些不足？

**答：**

第一，营养估算还不是医学级精度，后续可以接更权威食物营养库。第二，推荐权重目前是工程启发式，后续可以用标注数据做 NDCG 或 Hit Rate 评估。第三，微信登录和生产部署还需要更严格的安全校验。第四，VLM/LLM 依赖外部服务，后续可以增强本地模型和缓存。

## 8. 一句话收束

如果最后只剩 15 秒，可以这样说：

> ByteSavor 的重点不是接了几个 AI 接口，而是把饮食任务做成可执行、可追踪、可反馈的工程闭环。识别之后能校正，推荐之后能执行，吃完之后能记录，评分之后能学习，这就是我们项目的核心价值。

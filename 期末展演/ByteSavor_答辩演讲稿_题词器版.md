# ByteSavor 答辩演讲稿（题词器版）

适配：5 页 PPT + 手机/网页演示，总时长约 8-10 分钟。

## 第 1 页：项目定位

各位老师同学好，我们的项目叫 ByteSavor，完整题目是“基于多模态 Agent 的全场景饮食全链路解析系统”。

我们一开始不是想做一个普通菜谱 App，而是从一个很日常的问题出发：用户看到食材、看到一顿饭、或者在外面看到一道菜之后，系统能不能继续帮他完成后面的决策。

所以 ByteSavor 做的是一条完整链路：先看懂食物，再结合用户目标推荐，再生成清单或用餐计划，最后把已经吃过的内容和用户反馈记下来。这样下一次推荐就不是从零开始，而是会越来越贴近这个用户。

第一页底部这条流程就是我们想强调的完整闭环：拍照识别之后，不是停在“识别到了什么”，而是继续进入智能决策，推荐菜谱，再生成清单和用餐计划；用户在首页确认这一餐已经完成以后，才写入营养记录；最后通过评分和原因形成偏好学习。这个链路是我们和普通识别工具、菜谱工具最不一样的地方。

这一页想表达的是：它不是单个识别工具，也不是单个推荐工具，而是面向饮食场景的多模态 Agent。

## 第 2 页：Baseline 到闭环

这一页我们参考最初 ByteSavor 方案里的 baseline 思路来讲。

原始 baseline 的问题，不是说市面上完全没有相关 App，而是这些能力通常是断开的。

比如识别工具只能告诉用户“这是什么”，菜谱工具只做单点搜索，营养工具需要用户手动换算，购物清单还要自己整理，用户反馈也不会回到下一次推荐。

结果就是从信息到行动之间有很多手动跳转。现场演示时也会变成“我打开了很多个工具”，但它们之间没有真正的流程关系。

ByteSavor 的改进点是把这些节点接起来：B 是 Sense，处理图片和文本输入；Y 是 Decision，做推荐和营养缺口判断；T 是 Task，生成清单、用餐计划和执行动作；E 是 Feedback，把评分和偏好写回系统。

所以这里不是把几个功能放在同一个 App 里，而是从 baseline 的离散工具，变成一个可执行、可解释、可复盘的闭环。

## 第 3 页：技术框架：从前端体验到 Agent 编排

这一页我想把架构层次讲清楚。它不是“前端调一个后端接口”这么简单，而是从用户体验一直到 Agent 编排和长期记忆分了几层。

第一层是前端体验层。用户看到的是首页总控台、拍照识别、营养看板、品质鉴定、探店向导、文本导入和 AI 助手。这一层按角色组织，保证家庭做饭、健康管理、买菜、探店这些场景都能独立演示。

第二层是 API 接入层，也就是 FastAPI routers。它负责鉴权、参数校验和统一返回格式，接口包括 auth、sense、decision、meals、feedback、nutrition、quality、guide 和 agent。这里我们已经不是前端本地假登录：注册会在 MySQL 的 users 表创建账号，同时创建 profile；登录会查数据库并签发 JWT，所以可以注册不同账号，切换账号后看到的是各自的画像、用餐记录和偏好记忆。

第三层是 Agent 编排层。这里用的是 LangGraph runtime。它不是直接生成一个最终答案，而是有 planner、tool_start、tool_result 和 final 这些事件，每一步都会留下 trace_id、stages、latency 和 degraded 信息。

第四层是工具服务层，也就是 B-Y-T-E。B 是 Better Perception，更敏锐的感知；Y 是 Yielding Decisions，高效决策；T 是 Task Automation，任务执行；E 是 Evolving Feedback，反馈进化。这里对应的是 VLM 识别、推荐引擎、清单/三餐计划、偏好学习这些服务。

第五层是数据与记忆层。MySQL 里保存用户、画像、菜谱、用餐记录和偏好记忆；Redis 做缓存；菜谱数据提供基础推荐候选。

第六层是外部模型层。VLM 负责看图，LLM 负责意图理解、探店讲解和偏好解析。如果模型失败，我们记录降级，而不是伪造 mock 数据。

这一页还想补充我们的技术难点。第一是多模态模型返回内容不稳定，所以我们不能直接把模型文本展示给用户，而是要解析成结构化食材、分量、置信度和营养字段，再给用户删除和修订。

第二是状态边界。识别、推荐和导出清单都不能直接等于“已经吃了”，否则健康看板会被污染。所以我们把“生成清单”“加入用餐计划”和“完成这一餐”分成不同动作。只有首页用餐计划里点击完成，才会创建 completed 的 MealRecord，健康看板也只统计 completed 记录。

第三是推荐解释和降级。推荐结果里不只返回菜谱，还会带 reasons 和 fallback 标记；Agent 结果里也会带 stages 和 events。这样如果外部模型慢了、失败了，前端不是只显示“网络异常”，而是能知道是哪一个阶段出了问题。

第四是长期记忆一致性。营养记录和偏好记录是两个不同的长期记忆：一个回答“今天吃了什么”，一个回答“用户喜欢什么”。它们都来自用户确认后的行为，而不是凭模型猜测。

所以这里的 Agent 不是只有聊天框，而是一个能编排多个工具、处理降级、并且能把反馈写回长期记忆的闭环。

## 第 4 页：Agent 深度

这一页我想多解释一下，我们为什么说它是 Agent，而不是一个普通的 API 调用项目。

第一层是输入理解。用户可以输入自然语言，也可以上传图片。比如“家里有牛肉和南瓜，30 分钟做个减脂餐”，系统会先解析出食材、时间限制、饮食目标和当前任务模式。我们最新修复后，Agent 会更重视用户明确说出的核心食材，所以这个例子里首推会优先覆盖“牛肉”和“南瓜”，而不是只因为低碳高蛋白就推荐一盘芹菜牛肉。

第二层是工具编排。Agent 不是自己凭空生成答案，而是选择调用后端已有工具：sense 负责识别，decision 负责推荐，task 负责清单和计划，nutrition 负责餐盘营养，quality 负责品质判断，guide 负责探店讲解。

这里的“可追踪”是有具体返回结构的。每一次 Agent 调用都会返回 trace_id、conversation_id、events 和 stages。events 里会记录 plan、tool_start、tool_result 和 final；stages 会把 tool_result 整理成 stage、status、latency_ms、error_code 和 retry_count。

比如 decision 成功，就会出现 status 等于 success，并记录这一步耗时多少毫秒；如果 sense 调用 VLM 失败，会记录 error_code，比如 VLM_UNAVAILABLE 或具体异常名，同时整个结果的 degraded 会变成 true。前端就可以提示“视觉识别暂不可用，但推荐或清单部分仍可继续”，而不是让用户以为整个系统崩了。

我们的兜底分两层：第一层是 Agent 级别的兜底，某个工具失败时记录错误和 degraded，尽量返回已有的部分结果；第二层是业务级兜底，比如推荐引擎在硬过滤没有结果时会 fallback 到相近菜谱，并给结果打 fallback 标记。这样演示时如果外部模型慢了，我们可以切换到已有测试图片、角色页面或 Swagger 接口，同时解释是哪一层降级。

第三层是长期记忆。系统不是每次都重新开始。用户完成一餐后，会写入 MealRecord，健康看板只读取 completed 的记录；用户评分和文字原因会进入 preference memories。比如“喜欢清淡少油、高蛋白”会变成 liked light、high_protein；“太油腻”会变成 avoid oily。下一轮推荐会读取这些信号，对菜谱加权或降权。

所以独立页面保证每个能力可以测试，Agent 负责把这些能力串起来，这是我们项目里 Agent 的真实定位。

## 第 5 页：角色化测试、软件规模与现场演示

最后一页把测试、规模和演示路线放在一起。

我们的测试是按角色设计的。家庭做饭用户对应识别、校正和推荐；健康管理用户对应加入计划、完成一餐、删除记录和营养汇总；买菜用户对应品质鉴定；探店用户对应菜品故事、口味和吃法；长期个性化用户对应偏好记忆测试。

规模这里我想解释一下行数。核心代码不是简单堆出来的。目前核心手写代码约 1.23 万行，其中后端 Python 约 3,636 行，前端 Vue 和 JS 约 7,935 行，测试约 724 行。全工程约 15 万行，主要是因为菜谱数据 `recipes.json` 本身有 138,252 行，这部分代表我们的数据规模，不是业务代码凑数。

源文件方面，后端、前端和测试的主要源文件接近一百个，自动化测试文件 11 个，已经超过课程要求。最新一次针对 Agent、推荐、用餐记录、偏好记忆等核心链路的验证里，Agent/运行时相关 17 个测试通过，带数据库的核心链路 16 个测试通过，两个 H5 前端构建也通过。

接下来演示我会按一条主线走：先设置用户画像，再拍照识别，校正后生成清单，查看本次食材营养和今日缺口；然后把本次食材加入某个餐时，比如午餐或加餐；回到首页用餐计划点击完成，这时才更新健康看板；最后评分并写原因，让系统形成偏好记忆。

如果时间允许，我会再快速展示品质鉴定和探店向导。这样五类角色场景和我们的测试也能一一对应。

## 软件演示题词器

现在我打开项目首页。

这里首页是总控台，上面有今日状态，下面是不同角色入口。我们先从设置进入。

如果要展示账号系统，我会先退回登录页。这里注册一个新的微信ID/OpenID，后端会真实写入 users 和 profiles 表；已有账号再登录时不是重新创建，而是查到原用户并返回 JWT。演示版为了方便，用 OpenID 作为账号标识，没有把密码明文存进数据库。生产环境如果接微信小程序，应该由前端传 code，后端调用 code2session 换取 openid；如果做普通账号密码，也应该只存 bcrypt/argon2 这类哈希，不能存明文密码。

这里可以看到饮食目标和身体数据。比如减脂、均衡、增肌会对应不同热量和蛋白目标；如果用户有自己的目标，也可以直接自定义。

接下来回到首页，进入拍照识别。我上传 demo_tests 里面准备好的图片。

识别结果出来后，这里不是直接进入摄入数据库，而是先让用户校正。因为视觉模型可能会把同一个物体识别成多个候选，比如把一个西瓜拆成多个概率不同的识别项，所以我们加了删除和修订，这一步保证后面的营养计算更可信。

现在我确认并生成清单。这个页面有三块信息：第一块是本次食材本身的营养，第二块是这些营养占每日目标多少，第三块是今天已经摄入和还缺什么。这里的目标来自用户画像，不是固定写死。

这里我不会直接点“摄入”，而是把它加入今天某一个餐时计划。因为识别和导出清单不等于用户真的吃了。加入计划以后，我回到首页的今日用餐计划，可以看到早餐、午餐、晚餐，也可以有加餐、宵夜和自定义餐时。

现在我点击“完成这一餐”。这个动作才会更新今日摄入，同时生成一条 completed 用餐记录，并且根据本餐使用的食材扣减库存。

接着系统会问我这餐怎么样。我选择 5 分，并写一个原因。这个原因不是只保存文本，后端会解析成结构化偏好，比如 high_protein、light 或 avoid oily。

现在进入健康看板，可以看到今日摄入已经更新。如果发现这条记录不对，也可以删除，删除后不会继续计入统计。

如果演示 AI 助手，我会输入“牛肉南瓜减脂30分钟”。系统会解析出牛肉、南瓜、减脂和 30 分钟，推荐结果会优先覆盖用户明确给出的核心食材，比如首推南瓜牛肉相关菜谱，并在对话里展示 stage 和推荐过程。

最后我展示一下探店向导。上传菜品图片后，系统先识别菜名，再补充历史故事、口味技法和最佳吃法。这个页面适合外出吃饭或者学习菜品文化。

## 结尾

最后总结一下，ByteSavor 的重点不是简单接几个 AI 接口，而是把饮食场景做成一条可验证的工程闭环。

识别之后能校正，推荐之后能执行，吃完之后能记入营养，评分之后能形成偏好记忆。这样系统下一次推荐时会真正参考这个用户，而不是每次都重新开始。

以上就是我们的展示，谢谢大家。

## 可能被问到的问题

### 这和普通菜谱 App 有什么区别？

普通菜谱 App 通常只解决“搜菜谱”。我们这里从当前食材、用户目标、营养缺口和历史偏好一起做决策，并且连接了清单、用餐记录和长期记忆。

### 你们的 Agent 体现在哪里？

我们不是把所有逻辑写在一个聊天接口里，而是先把识别、推荐、清单、营养、品质、探店做成独立工具，再由 Agent 根据用户输入选择和编排工具。这样既能单独测试，也能支持一句话跨场景完成任务。

### 营养数据是否完全准确？

我们定位是健康建议级估算，不是医学级诊断。系统会根据识别分量和营养表计算，并且允许用户修订和删除错误记录，保证长期统计尽量可信。

### 为什么一定要完成这一餐才计入？

因为拍到一张食物图片不代表用户真的吃了，导出清单也只是准备动作。我们把识别、推荐、清单、加入用餐计划和完成这一餐分开，只有用户在首页用餐计划里明确点“完成”，才写入数据库并计入健康看板。

### 偏好数据库有什么价值？

用户评分和文字原因会进入 `preference_memories`。下次推荐时，系统会读取 liked 和 avoid 信号，对符合偏好的菜加权，对不喜欢的口味降权。这是我们闭环里非常关键的一步。

### 注册和登录是真实的吗？密码怎么处理？

注册和登录是真实落库的。演示版用微信ID/OpenID 作为账号标识，注册时写入 MySQL 的 `users` 表，并创建对应 `profiles`；登录时按 OpenID 查库，成功后返回 JWT。当前没有明文密码字段，所以也没有把密码存在数据库里。生产环境如果接微信，应改成前端传 code，后端 code2session；如果做账号密码登录，需要只保存哈希密码，不能保存明文。

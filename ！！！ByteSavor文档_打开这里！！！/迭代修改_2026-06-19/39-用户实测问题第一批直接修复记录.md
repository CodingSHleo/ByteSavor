# ByteSavor 用户实测问题第一批直接修复记录

日期：2026-06-21

依据：`38-批次A-D复审问题清单.md`

本批目标：先修用户能立刻测出的断链问题，并把推荐逻辑从“单纯分数排序”调整为“数据库候选 + 食材硬约束分层 + 可选 LLM 重排”。

---

## 1. 推荐逻辑修复

### 已修复

1. `牛肉韭黄` 不再让只命中 `牛肉` 的菜压过 `韭黄` 菜。
2. 推荐排序改为分层：
   - 第一层：覆盖全部用户现有食材。
   - 第二层：覆盖更具体/关键的用户食材，例如 `韭黄`、`南瓜`。
   - 第三层：只覆盖泛主料的部分匹配，例如只命中 `牛肉`。
   - 第四层：无匹配仅作为 fallback。
3. 每道推荐都返回自身 `_meta`：
   - `matched_ingredients`：这道菜实际用到的用户现有食材。
   - `missing_ingredients`：用户给了但这道菜没用上的食材。
   - `purchase_suggestions`：菜谱需要但用户没给的食材，可作为“建议购买”。
4. 新增可选 LLM 重排层：
   - 文件：`app/services/llm_rerank.py`
   - DeepSeek 只能从数据库候选 `recipe_id` 中排序，不能编造新菜。
   - 未配置 `LLM_API_KEY` 时自动回退本地排序，演示不阻塞。

### 架构真实性说明

当前主推荐接口 `/v1/decision/meal-plan` 的基础能力仍是数据库菜谱召回和本地规则排序。DeepSeek 现在作为可选 rerank，不是唯一推荐来源。这样更符合工业化边界：

- 数据库保证菜谱真实存在；
- 规则层保证库存/食材硬约束；
- LLM 负责更像人的排序判断和解释；
- LLM 失败时不影响基础推荐可用性。

## 3. 首页刷新推荐修复

### 已修复

1. `ApiService.generateMealPlan(ingredients, options)` 支持：
   - `refresh`
   - `excludeRecipeIds`
2. 首页点击“刷新/生成推荐”时传：
   - `refresh: true`
   - 当前推荐列表的 recipe_id 作为 `exclude_recipe_ids`
3. 后端 `DecisionRequest` 新增：
   - `exclude_recipe_ids`
4. 后端收到 refresh 时会尝试避开当前结果，候选不足时保留最佳匹配，避免为了刷新而推荐无关菜。

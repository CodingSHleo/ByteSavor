## 1. 一句话结论

ByteSavor 当前已经不再是“前端调用几个 AI API”的简单应用，而是正在形成一个可审查、可降级、可评估、可观测的多模态饮食 Agent 工业化框架。

目前已经完成两块核心底座：

1. **Skill 工业化底座**：每个 Agent 工具都有 `SkillDescriptor`、注册校验、统一超时/重试/错误码、事件追踪。
2. **受控 LLM Planner / Soft Judge**：DeepSeek 不再只是聊天接口，而是可以作为可选 planner/judge，但被严格限制在候选 Skill 和数据库候选结果之内。

还未完成两块体验和性能增强：

1. **VL 速度与缓存**：需要继续优化千问 VL 的 cache key、模型/prompt 版本、观测字段和前端压缩反馈。
2. **前端可解释展示**：需要把后端的 planner/skill/evaluator/cache/memory 等事件真正展示给用户和评委看。

---

## 2. 项目当前定位

ByteSavor 的目标不是单点菜谱推荐，而是围绕以下链路建立饮食 Agent：

```text
用户输入 / 图片
  -> VLM 感知食材
  -> Agent Planner 选择 Skill
  -> Skill 执行库存、推荐、营养、清单、社区等能力
  -> Evaluator / Judge 审查结果
  -> 前端展示推荐、理由、记忆、时间线
  -> 用户纠错/评分回流偏好与记忆
```

核心约束仍然保持务实：

| 约束 | 当前决策 |
|---|---|
| 视觉模型 | 只接千问 VL API，不做本地 CNN/ONNX 降级 |
| 逻辑模型 | DeepSeek 作为可选 planner/rerank/judge/assistant，不做无边界自由生成 |
| 数据层 | MySQL 业务数据，Redis 缓存/会话状态 |
| 推荐边界 | 数据库召回 + 规则排序 + 可选 LLM rerank，不允许 LLM 编造数据库不存在的菜谱 |
| 演示目标 | 不追求炫技 WebSocket/SSE，优先保证稳定、可解释、可验证 |

## 5. v6-01 已完成：Skill 工业化底座

修复记录：

- `docs/迭代修改/42-v6-Skill工业化底座修复记录.md`

### 5.1 核心变化

#### 5.1.1 SkillDescriptor 从说明变成执行契约

文件：

- `app/agent/skill_descriptor.py`

新增字段：

```python
timeout_ms: int
max_retries: int
retryable_errors: list[str]
degrade_on_error: bool
category: str
```

这使每个 Skill 都有明确的执行边界：

| Skill | 分类 | 超时 | 重试 |
|---|---|---:|---:|
| `sense` | perception | 12000ms | 1 |
| `decision` | decision | 10000ms | 0 |
| `task` | task | 6000ms | 0 |
| `nutrition` | perception | 12000ms | 1 |
| `quality` | perception | 12000ms | 1 |
| `guide` | perception | 12000ms | 1 |
| `inventory` | memory | 5000ms | 0 |
| `favorites` | memory | 5000ms | 0 |
| `recipe_check` | decision | 7000ms | 0 |

#### 5.1.2 ToolRegistry 必须绑定 descriptor

文件：

- `app/agent/tools.py`

当前能力：

```python
tools.register("decision", decision_tool)
tools.descriptor("decision")
tools.describe()
tools.has("decision")
```

约束：

- 未在 `SKILL_DESCRIPTORS` 中声明的工具不能注册。
- 注册未知工具会抛出 `ValueError("Unknown skill descriptor: <name>")`。
- `describe()` 返回前端和 planner 可消费的结构化 descriptor。

意义：

> Planner 不能在一堆裸函数里盲选，所有工具必须先进入受控 Skill 注册体系。

#### 5.1.3 统一 Skill 执行 wrapper

文件：

- `app/agent/tools.py`

新增：

```python
async def execute_tool(registry: ToolRegistry, name: str, state: AgentState) -> SkillExecutionResult
```

统一处理：

- `asyncio.wait_for` 超时；
- 最多一次 retry；
- 错误码归一化；
- latency 统计；
- descriptor 注入事件；
- 成功/失败统一返回 `SkillExecutionResult`。

#### 5.1.4 Runtime 与 LangGraph 事件统一

文件：

- `app/agent/runtime.py`
- `app/agent/langgraph_runtime.py`

当前 `tool_result` 事件示例：

```json
{
  "type": "tool_result",
  "phase": "EXECUTING",
  "tool": "sense",
  "skill": {
    "name": "sense",
    "category": "perception",
    "timeout_ms": 12000
  },
  "status": "error",
  "latency_ms": 1,
  "retry_count": 0,
  "error_code": "VLM_NOT_CONFIGURED",
  "summary": {
    "ingredient_count": 0
  },
  "step": 0,
  "message": "VLM_NOT_CONFIGURED"
}
```

这让前端时间线和答辩展示可以真实呈现：

- 选了哪个 Skill；
- 属于感知/决策/记忆/任务哪类；
- 执行多久；
- 是否 retry；
- 是否 degraded；
- 错误码是什么。

#### 5.1.5 `sense` 始终注册

文件：

- `app/routers/agent.py`

之前问题：

```python
if settings.vlm_api_url:
    tools.register("sense", sense_tool)
```

这会导致没配 VLM 时 `sense` 直接消失，planner 和前端无法解释。

当前逻辑：

- `sense` 始终注册；
- 没图片：`NO_IMAGE`；
- 没配置 VLM：`VLM_NOT_CONFIGURED`；
- VLM 无结果：`VLM_UNAVAILABLE`；
- API 返回 degraded，而不是工具不存在。

#### 5.1.6 主 agent 复审补丁：Skill 错误后停止继续规划

复审时发现：

> `LangGraphAgent` 在 `sense` 失败后，可能继续回 planner 执行 `decision`，造成“感知失败但仍然推荐”的误导。

已修复：

- `plan_next_action()` 在 `state["errors"]` 非空时直接 `finish`。
- `AgentRuntime` 的错误路径也统一进入 `_finish_run()`。
- 新增测试：`test_langgraph_stops_after_skill_error_instead_of_continuing_to_decision`。

## 6. v6-02 已完成：受控 LLM Planner 与 Soft Judge

修复记录：

- `docs/迭代修改/43-v6-LLMPlanner与Judge修复记录.md`

### 6.1 核心设计原则

DeepSeek 可以参与规划和评估，但不能变成无边界自由生成器。

边界如下：

| 能做 | 不能做 |
|---|---|
| 在候选 Skill 里选择下一步 | 发明不存在的工具 |
| 对已有结果做软性评估 | 阻断主流程 |
| 对数据库候选做重排 | 编造数据库不存在的菜谱 |
| 失败后回退规则 planner | 因 LLM 不可用导致 API 失败 |

### 6.2 Descriptor 候选动作生成

文件：

- `app/agent/planner.py`

新增：

```python
build_candidate_actions(state, skill_descriptors)
```

候选动作来自：

```python
ToolRegistry.describe()
```

不是手写开放工具列表。

候选会根据以下字段过滤：

- `requires_image`
- `requires_user`
- `intent_keywords`
- `input_fields`
- `completed_tools`

### 6.3 LLM Planner

文件：

- `app/agent/llm_planner.py`

核心接口：

```python
choose_action_with_llm(state, candidates)
select_next_action(state, skill_descriptors)
```

默认关闭：

```python
agent_llm_planner_enabled: bool = False
```

只有同时满足以下条件才尝试 LLM planner：

1. `agent_llm_planner_enabled=True`
2. `llm_api_key` 非空
3. `llm_api_url` 非空
4. descriptor 候选动作非空

失败回退：

| 情况 | 结果 |
|---|---|
| LLM 未启用 | `planner_source="rule"` |
| 无 key/url | 不联网，走规则 |
| HTTP 失败 | `rule_fallback` |
| JSON 解析失败 | `rule_fallback` |
| LLM 选择候选外工具 | `rule_fallback` |

### 6.4 感知优先约束

主 agent 复审时新增的重要约束：

> 对图文混合请求，如果用户要求“识别图片并推荐”，候选动作第一步只暴露 `sense`，LLM 不能跳过感知直接选择 `decision`。

原因：

- 如果图片是主要输入，跳过 `sense` 直接推荐会使 Agent 变成纯文本推荐；
- 这会破坏“感知与认知解耦”的架构原则；
- 也会导致评委质疑 VLM 是否真的进入主流程。

新增测试：

- `test_image_identify_recommend_candidates_force_sense_before_decision`
- `test_llm_cannot_skip_required_sense_for_image_recommendation`

### 6.5 Soft Judge

文件：

- `app/agent/llm_judge.py`

默认关闭：

```python
agent_llm_judge_enabled: bool = False
```

启用后在硬规则 evaluation 之后、final 之前追加：

```json
{
  "type": "soft_judge",
  "phase": "EVALUATING",
  "verdict": "WARN",
  "scores": {
    "instruction_following": 3.5
  },
  "issues": ["偏好解释不足"],
  "suggestions": ["补充原因"]
}
```

硬边界：

- 不改变 `status`；
- 不改变 `termination_reason`；
- 不写入硬错误；
- 异常时最多追加 `SKIPPED` 事件；
- 不新增菜谱；
- 不调用外部 DB。

## 8. 当前创新点总结

### 8.1 工业化 Skill 框架

创新点不是“写了几个函数”，而是每个能力都进入统一 Skill 生命周期：

```text
Descriptor -> Registry 校验 -> Planner 候选 -> Execute wrapper -> Event -> Evaluator/Judge -> Final
```

这比直接 `if/else 调接口` 更接近工业 Agent 框架。

### 8.2 受控 LLM，而非自由生成

DeepSeek 当前被放在受控位置：

| 位置 | 作用 | 边界 |
|---|---|---|
| assistant | 对话建议 | 不能替代主推荐链路 |
| rerank | 重排 DB 候选 | 不能新增 recipe_id |
| planner | 选择候选 Skill | 不能发明工具 |
| judge | 软性评估 | 不能阻断主流程 |

这比“让 LLM 直接回答”更安全，也更适合答辩说明。

### 8.3 感知与认知解耦

当前保持：

- VLM：只负责看图识别；
- LLM：只负责规划、重排、评审；
- DB/rules：负责真实菜谱和硬约束；
- Evaluator：负责硬规则检查；
- Judge：负责软性质量反馈。

### 8.4 可观测执行时间线

后端 events 已经具备展示基础：

- `plan`
- `tool_start`
- `tool_result`
- `evaluation`
- `soft_judge`
- `final`

每个 `tool_result` 可带：

- `skill.category`
- `latency_ms`
- `retry_count`
- `error_code`
- `summary`

前端还需要继续把这些字段展示出来，这是 v6-04 的重点。

## 10. 当前风险与专家审阅重点

### 10.1 LLM Planner 的收益边界

当前 LLM Planner 已经受控，但默认关闭。

请专家重点看：

1. 当前 candidate generation 是否足够合理？
2. 是否应该在演示环境开启 `agent_llm_planner_enabled`？
3. 如果开启，是否需要限制只对复杂多约束请求启用，而不是每轮都调用？

建议倾向：

> 答辩演示可以开启，但生产默认关闭或按复杂度启用，避免不必要延迟和成本。

### 10.2 Soft Judge 的定位

当前 Soft Judge 不阻断主流程，只追加事件。

请专家重点看：

1. Judge 是否应该在用户请求级别开启？
2. 是否应该只在 Eval/offline pipeline 使用，而不是每个线上请求使用？
3. 如果线上开启，是否需要采样？

建议倾向：

> 运行时 hard evaluator 必须在线；LLM Judge 更适合作为演示增强或离线 Eval 的裁判，不建议所有请求默认开启。

### 10.3 VLM 速度优化仍未完成

这是当前还没收口的性能点。

专家可重点审：

1. cache key 是否应包含 prompt version 和模型；
2. base64 图片是否应先上传对象存储而不是直接进 API；
3. 图片压缩参数是否适合识别准确率；
4. VLM 超时后是否应该让用户确认重试，而不是继续推荐。

### 10.4 完整黑箱 Eval 还不充分

当前 Eval quick 是 10 条，不等于完整 30-50 条黄金用例。

专家可重点审：

1. Eval case 矩阵是否覆盖真实场景；
2. LLM Judge 是否可复用运行时 judge；
3. 评分维度是否应该加权；
4. 是否需要 human alignment 校准。

## 12. 当前建议答辩表述

可以这样讲：

> ByteSavor 的创新点不是简单调用 DeepSeek 和千问 VL，而是把它们封装进一个受控的 Agent 工业化框架。我们把系统拆成感知、决策、记忆、任务、评估等 Skill，每个 Skill 都有 descriptor、输入输出、超时、重试、错误码和事件追踪。DeepSeek 不能随意生成菜谱，它只能在候选 Skill 中规划、对数据库候选做重排、对结果做软性评审；千问 VL 只负责感知。整个流程可以被事件时间线审查，也可以被 Eval Pipeline 回归验证。

如果评委问“这是不是 prompt 工程”，可以回答：

> 不是单纯 prompt 工程。Prompt 只是 LLM 的局部输入，ByteSavor 的核心是外层 harness：Skill 注册、descriptor 约束、planner 候选、执行 wrapper、错误降级、事件可观测、hard evaluator、soft judge、Eval 回归。即使 LLM 不可用，系统仍能通过规则 planner 和数据库推荐链路工作。

如果评委问“DeepSeek 是否真的进入主 Agent”，可以回答：

> 当前 DeepSeek 已经进入三个受控位置：planner、rerank、judge。但默认开关关闭，避免无 key 或网络不稳定影响演示。开启后，它只能在候选 Skill 里选择，不允许发明工具或菜谱；失败自动回退规则 planner。

## 13. 后续执行建议

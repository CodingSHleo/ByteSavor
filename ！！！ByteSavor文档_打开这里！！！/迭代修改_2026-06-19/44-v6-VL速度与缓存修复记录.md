# v6-03 VL 速度与缓存修复记录

日期：2026-06-21

## 修复范围

- 后端 VLM 感知链路增加模型和 prompt 版本化缓存 key。
- 后端返回缓存、耗时、模型、prompt version、图片指纹等观测字段。
- 前端食材识别页调整 H5 图片压缩参数，并补充压缩、推理、缓存命中、完成状态。
- 未实现或修改 LLM Planner/Judge，未新增本地 CNN/ONNX 降级。

## Cache Key 组成

`app/services/vlm/__init__.py` 当前使用：

```python
fingerprint = _image_hash(image_url)
cache_key = make_key("vlm", settings.vlm_model, FOOD_ANALYSIS_PROMPT_VERSION, fingerprint)
```

其中：

- `fingerprint` 是图片 URL 或 base64 data URL 的 MD5 截断 hash。
- `settings.vlm_model` 参与 key，模型切换不会复用旧模型结果。
- `FOOD_ANALYSIS_PROMPT_VERSION = "food-analysis-v1"` 参与 key，后续 prompt 改动时升级版本即可隔离旧缓存。
- 返回给前端的是 `image_fingerprint` hash 和 `cache_key`，不返回也不记录原始 base64。

## 观测字段

`analyze_food()` 成功返回包含：

- `cache_hit`
- `cache_key`
- `latency_ms`
- `model`
- `prompt_version`
- `image_fingerprint`

cache hit 时 `latency_ms` 使用本次 cache 读取耗时，不复用首次 VLM 推理耗时。

## 为什么不做本地 CNN 降级

本轮目标是把外部 VLM 依赖包装成可观测、可复用、版本隔离的工程链路，而不是新增识别模型。引入本地 CNN/ONNX 会增加模型资产、端侧/服务端推理路径、准确率校准和降级一致性成本，也会违反 v6-03 任务书的明确边界。

## 前端压缩与状态

H5 图片压缩参数调整为：

- `maxW = 720`
- `canvas.toDataURL("image/jpeg", 0.68)`
- 小于 720 像素宽的图片不放大。

识别页补充状态：

- `正在压缩图片...`
- `图片已压缩，准备调用视觉模型...`
- `VLM 多模态模型推理中...`
- cache 命中时展示 `命中缓存，已快速识别`
- 完成时展示 `识别完成，请确认 X 种食材`

如果 API 返回 `latency_ms`，页面显示 `缓存命中/实时推理 · Nms`。

主 agent 复审补丁：

- H5 上传路径继续显示压缩状态。
- 非 H5 文件路径当前只是读取并转 base64，没有真正压缩，因此文案从 `正在压缩图片...` 调整为 `正在读取图片...`，避免误导。
- 完成状态直接带 `latency_ms`，例如 `识别完成 · 123ms，请确认 3 种食材` 或 `命中缓存，已快速识别 · 3ms`。

## 剩余风险

- 真实 VLM 网络耗时仍取决于外部 API、网络质量和模型服务负载。
- cache miss 的首轮请求仍可能较慢；本轮通过前端压缩和后端缓存降低重复识别成本。

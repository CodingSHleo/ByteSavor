# ByteSavor 用户实测问题总结与修复计划

日期：2026-06-21  
来源：用户本地实测反馈  
性质：真实产品缺陷，不是文档补充；先总结和计划，后续按优先级修复。

---

## 0. 总体判断

这轮问题不小，主要不是单点 bug，而是 **“后端能力已有雏形，但前端产品闭环和推荐/搜索/用户隔离逻辑没有真正打磨”**。

当前已经具备：

- 密码注册/登录。
- 社区发帖/点赞/评论/收藏/清点的基础 API。
- 菜谱推荐、菜谱库、用餐计划、收藏 API。
- Agent/Loop/Eval 的工程化框架。

但用户实际体验暴露出：

- 新用户数据隔离不可信。
- 推荐质量不符合输入食材。
- 搜索召回太窄。
- 刷新推荐没有真正刷新。
- 用餐计划状态不可切换。
- 社区图片、收藏/点赞交互动效和取消逻辑不完整。
- 菜谱库外层缺少“加入今日用餐计划”。
- 底部 tab 图标尺寸/位置不一致。
- AI 助手回复不够约束输入食材。

这说明 v5 只能算“接口和基础闭环可跑”，还没达到“产品可用闭环”。

## 1. 用户反馈问题清单

### 1.1 新注册用户里面已有数据

用户现象：

> 新注册的用户里面就有数据了。

初步定位：

- 后端 `MealRecord`、`Inventory`、`Favorites` 等表本身按 `user_id` 查询，理论上支持隔离。
- 但前端多处页面仍可能展示：
  - 本地 mock/静态数据。
  - 全局 seed 菜谱。
  - 上一个用户残留在 storage/store 中的数据。
  - 旧 token 未清理导致新注册后读到旧用户数据。

重点排查文件：

- `bsapp/src/store/auth.js`
- `bsapp/src/pages/login/login.vue`
- `bsapp/src/pages/register/register.vue`
- `bsapp/src/pages/health-dashboard/health-dashboard.vue`
- `bsapp/src/pages/explore/explore.vue`
- `bsapp/src/pages/inventory/inventory.vue`
- `bsapp/src/pages/favorites/favorites.vue`
- `app/services/meal_memory.py`
- `app/services/inventory.py`
- `app/services/favorites.py`

修复方向：

1. 登录/注册成功后必须清理旧用户缓存，再写入新用户。
2. 登出时清理所有用户相关 storage：
   - `auth_token`
   - `user_id`
   - `username`
   - `inventory`
   - `recognition_result`
   - 推荐缓存
   - 今日计划缓存
3. 页面加载时，凡是用户私有数据必须只从后端接口读取，不允许 fallback 到 mock 数据伪装成真实数据。
4. 明确区分：
   - “菜谱库公共 seed 数据”可以新用户可见。
   - “库存、收藏、用餐记录、营养记录、社区 liked_by_me”必须按用户隔离。

验收标准：

- 注册全新账号后：
  - 我的收藏为空。
  - 当前库存为空。
  - 今日用餐记录为空。
  - 营养记录为 0 或空状态。
  - 社区公共帖子可见，但 `liked_by_me=false`。

### 1.2 社区应支持上传图片

用户现象：

> 社区应该支持上传图片。

当前代码状态：

- 后端 `CommunityPost.images` 已有 JSON 字段。
- `CommunityPostRequest.images` 允许最多 9 张。
- 前端 `community-publish.vue` 的 `form.images` 永远是空数组，没有选择图片、预览、删除。

涉及文件：

- `bsapp/src/pages/community-publish/community-publish.vue`
- `bsapp/src/pages/community/community.vue`
- `bsapp/src/pages/community-detail/community-detail.vue`
- `app/routers/community.py`
- `app/services/community.py`

修复方向：

P0 演示方案：

- 前端使用 `uni.chooseImage` 选择图片。
- H5 环境压缩为 base64/data URL 存入 `images`。
- 发布时随 `images` 写入后端。
- 列表展示首图缩略图。
- 详情展示图片网格。

P1 生产方案：

- 接入对象存储或本地上传接口。
- 后端保存 URL，不保存大 base64。

本轮建议先做 P0，因为课程演示更需要可见效果。

验收标准：

- 发布社区帖时可选 1-9 张图。
- 发布前可预览和删除。
- 列表卡片能看到首图。
- 详情页能看到全部图片。

### 1.3 点赞/收藏应有图标动效，点击一次成功，再点一次取消

用户现象：

> 点赞收藏应该有图标动效，点一次收藏成功，再点一次就取消。

当前代码状态：

社区：

- 后端点赞支持 like/unlike。
- 前端详情页已补过 `liked_by_me` 切换，但列表页仍没有点赞按钮。
- 社区收藏按钮只调用 `addFavorite()`，没有查询收藏状态，也没有再次点击取消。

菜谱库：

- `recipe-detail.vue` 已有 `toggleLike()`，可收藏/取消。
- `explore.vue` 外层卡片只有“收藏”，重复点击不会取消。

涉及文件：

- `bsapp/src/pages/community/community.vue`
- `bsapp/src/pages/community-detail/community-detail.vue`
- `bsapp/src/pages/explore/explore.vue`
- `bsapp/src/pages/recipe-detail/recipe-detail.vue`
- `bsapp/src/api/index.js`
- `app/routers/favorites.py`
- `app/services/favorites.py`

修复方向：

1. 前端统一实现 `toggleFavorite(targetType, targetId, snapshot)`：
   - 先读本地状态。
   - 未收藏：调用 `addFavorite()`，状态变 true。
   - 已收藏：调用 `removeFavorite()`，状态变 false。
2. 列表接口或页面初始化时批量拉收藏状态。
3. 点赞/收藏按钮统一使用 icon：
   - 空心心形：未收藏/未赞。
   - 实心心形：已收藏/已赞。
4. 加轻量动效：
   - 点击时 scale 0.92 -> 1.08 -> 1。
   - Toast 显示“已收藏/已取消收藏”。

验收标准：

- 社区列表、社区详情、菜谱库列表、菜谱详情都支持收藏状态切换。
- 同一按钮连续点两次，后端状态回到未收藏/未赞。
- 刷新页面后状态仍正确。

### 1.4 AI 助手推荐质量差：输入牛肉韭黄，推荐芹菜炒牛肉

用户现象：

> 我输入牛肉韭黄，给我推荐芹菜炒牛肉。

当前根因：

`app/services/decision.py` 中 `_rank()` 的总分：

```python
s = s_ing * 0.5 + s_tag * 0.3 + s_pref * 0.2
if s > 0.25: scored.append(...)
```

问题：

1. 食材匹配只是 50% 权重，不是硬约束。
2. 用户输入两个食材时，命中“牛肉”但没命中“韭黄”的菜仍可进入 Top。
3. `芹菜炒牛肉` 因为牛肉命中 + 标签分，可能排到前面。
4. 缺少“用户明确食材覆盖率”的强惩罚。
5. Fallback 会放宽太多，把“接近匹配”混到正常推荐里。

涉及文件：

- `app/services/decision.py`
- `app/routers/decision.py`
- `app/routers/agent.py`
- `app/agent/evaluator.py`
- `tests/test_decision.py`
- `tests/test_decision_memory_matching.py`

修复方向：

1. 用户输入食材是硬约束：
   - 输入 1 个食材：Top 结果必须命中这个食材。
   - 输入 2 个食材：Top 3 优先命中 2 个；如果没有，至少命中 1 个并明确标注“缺少韭黄”。
   - 输入 3 个以上：至少命中 50%。
2. 排序公式调整：
   - `user_coverage` 权重大幅提高。
   - `user_coverage < 0.5` 的候选降权或过滤。
3. 推荐解释必须显示：
   - 已匹配食材。
   - 未匹配食材。
   - 为什么仍推荐。
4. Agent 回复不能只说“找到 8 个菜谱”，要明确：
   - “完全匹配：韭黄炒肉丝 / 韭黄炒鸡蛋”
   - “部分匹配：芹菜炒牛肉，不作为首推”

验收标准：

请求：

```json
{"ingredients":["牛肉","韭黄"],"constraints":{"time_limit":30,"goal":"fat_loss"}}
```

Top 结果不得是 `芹菜炒牛肉`，除非数据库没有任何韭黄相关菜谱。但当前 seed 明确有：

- `韭黄炒肉末`
- `韭黄炒鸡蛋`
- `韭黄炒肉丝`
- `韭黄莴笋炒鸡蛋`

所以 Top 必须优先韭黄相关菜。

### 1.5 用餐计划无法切换，切换后数据逻辑不完整

用户现象：

> 点击用餐计划也无法切换，这里要做到能够切换，同时完善切换后数据逻辑。

当前代码状态：

- 后端 `MealRecord.meal_slot` 支持 `breakfast/lunch/dinner`。
- `plan_meal()` 创建计划。
- `complete_meal()` 标记完成并计入营养。
- `cancel_meal()` 只是改成 cancelled。
- 前端 `health-dashboard.vue` 主要展示已完成餐，没有完整“早餐/午餐/晚餐切换规划” UI。
- `recipe-detail.vue` 没有“加入早餐/午餐/晚餐”的直接入口。

涉及文件：

- `app/services/meal_memory.py`
- `app/routers/meals.py`
- `bsapp/src/pages/health-dashboard/health-dashboard.vue`
- `bsapp/src/pages/recipe-detail/recipe-detail.vue`
- `bsapp/src/pages/meal-nutrition/meal-nutrition.vue`
- `bsapp/src/api/index.js`

修复方向：

1. 后端新增/完善：
   - `PUT /v1/meals/{meal_id}` 或 `POST /v1/meals/{meal_id}/slot`
   - 支持切换 `meal_slot`。
   - 支持 planned/completed/cancelled 状态流转。
2. 前端健康看板增加分段控件：
   - 早餐
   - 午餐
   - 晚餐
3. 切换 meal slot 后：
   - 显示该 slot 的 planned/completed 记录。
   - 总营养仍按 completed 汇总。
   - planned 不计入已摄入，只显示“计划中”。
4. 菜谱详情和菜谱列表直接提供：
   - 加入早餐
   - 加入午餐
   - 加入晚餐
5. 用户可以把一个计划从午餐切到晚餐。

验收标准：

- 从菜谱详情添加到“晚餐计划”。
- 健康看板切到晚餐能看到该菜。
- 切到午餐看不到该晚餐计划。
- 点击“完成用餐”后计入营养汇总。
- 切换 meal slot 后刷新页面仍正确。

### 1.6 生成推荐 / 刷新推荐内容不更新

用户现象：

> 点击生成推荐，刷新推荐，内容根本没更新。

初步根因：

1. `health-dashboard.vue` 的推荐只在 `onLoad()` 里生成。
2. 刷新按钮可能只是重新调用同一批 ingredients。
3. 后端 `/v1/decision/meal-plan` 对未登录用户使用缓存：

```python
ck = cache.make_key("meal", json.dumps(ings), str(req.constraints))
```

4. 如果参数不变，推荐自然不变。
5. 前端没有 refresh nonce / exclude ids / shuffle seed。

涉及文件：

- `bsapp/src/pages/health-dashboard/health-dashboard.vue`
- `bsapp/src/pages/home/home.vue`
- `bsapp/src/api/index.js`
- `app/routers/decision.py`
- `app/services/decision.py`

修复方向：

1. 前端“刷新推荐”必须传：
   - `refresh: true`
   - `exclude_recipe_ids`
   - 或 `seed`
2. 后端支持 `constraints.refresh=true`：
   - 跳过缓存。
   - 对同分候选做稳定洗牌。
   - 排除已展示菜谱。
3. 前端状态更新：
   - 刷新中 loading。
   - 新推荐替换旧推荐。
   - 如果没有新候选，显示“已展示最匹配结果”。

验收标准：

- 连续点击刷新，Top 推荐至少在候选足够时发生变化。
- 不得仍显示完全相同的 8 条顺序。
- 若确实无更多结果，要有明确提示。

### 1.8 菜谱库搜索逻辑太窄，“韭黄炒蛋”匹配不到“韭黄炒鸡蛋”

用户现象：

> 菜谱库里面有韭黄炒鸡蛋，我搜索韭黄炒蛋却匹配不上。

当前代码：

`explore.vue`：

```js
list = list.filter(r => r.title.toLowerCase().includes(kw))
```

问题：

- 只做连续子串匹配。
- “炒蛋”和“炒鸡蛋”不等价。
- 没搜 ingredients。
- 没搜 tags。
- 没拼音/同义词/分词。

涉及文件：

- `bsapp/src/pages/explore/explore.vue`
- `bsapp/src/api/index.js`
- `app/routers/decision.py`
- `app/services/decision.py`
- `app/services/food_synonyms.py`
- `app/seed/recipes.json`

修复方向：

P0 前端增强：

- normalize query：
  - `炒蛋` -> `炒鸡蛋`
  - 去掉空格、标点。
  - 简繁/大小写基础处理。
- 搜索范围：
  - title
  - ingredients.name
  - tags
- Token 命中：
  - query 中每个关键 token 命中即可。

P1 后端搜索接口：

- `GET /v1/recipes?search=韭黄炒蛋`
- 后端统一搜索，避免前端一次拉全部再筛。
- 返回 score 和 matched_fields。

验收标准：

- 搜索 `韭黄炒蛋` 命中 `韭黄炒鸡蛋`。
- 搜索 `牛肉韭黄` 命中含牛肉或韭黄的菜，并优先双命中。
- 搜索 `炒蛋` 命中鸡蛋相关菜。

### 1.9 底部 tab 图标大小/位置异常

用户现象：

> UI 底下识别和社区图案没有跟其他的一个大小一个位置，是异常的。

当前配置：

`pages.json` tabBar：

```json
识别: static/icons/scan.png
社区: static/icons/knowledge.png
```

其他项：

```json
home.png / explore.png / profile.png
```

初步根因：

- PNG 资源本身画布尺寸或透明边距不一致。
- `scan.png` / `knowledge.png` 与其他 icon 没统一规格。
- uni-app 原生 tabBar 不支持单独 CSS 微调，必须统一图片资源尺寸。

涉及文件：

- `bsapp/src/pages.json`
- `bsapp/src/static/icons/*.png`

修复方向：

1. 统一所有 tab PNG：
   - 画布尺寸一致，例如 81x81 或 96x96。
   - 图形主体视觉尺寸一致。
   - 透明边距一致。
2. 如 PNG 不合适，基于现有 SVG 重新导出。
3. 检查 selectedIconPath 同步。

验收标准：

- 首页、识别、菜谱、社区、我的五个 tab 图标视觉中心一致。
- 图标大小一致。
- 选中/未选中不跳动。

## 2. 分阶段修复计划

### 2.0 迭代原则：不能只修表面问题

本轮修复必须采用“缺陷族治理”，不是看到一个按钮坏了就修一个按钮。

每个问题都要走四步：

1. **复现当前症状**
   - 记录用户路径、输入、页面、接口响应。
   - 例如：输入“牛肉韭黄”后 Top 推荐为什么是“芹菜炒牛肉”。

2. **定位根因层级**
   - 是前端状态没更新？
   - 是 API 没返回必要字段？
   - 是后端排序/过滤逻辑错？
   - 是缓存导致刷新无效？
   - 是用户态/Storage 串了？

3. **举一反三排查同类问题**
   - 收藏 toggle 有问题，就同时查：
     - 菜谱详情收藏
     - 菜谱列表收藏
     - 社区详情收藏
     - 社区列表收藏
     - 我的收藏页删除
   - 用餐计划 slot 有问题，就同时查：
     - 菜谱详情加入计划
     - 菜谱列表加入计划
     - 健康看板展示计划
     - 完成用餐后营养汇总
     - 取消/切换后是否还计入统计
   - 搜索召回有问题，就同时查：
     - 菜谱库搜索
     - 推荐检索
     - Agent 输入解析
     - 同义词标准化
     - Eval 用例覆盖

4. **沉淀成测试和验收项**
   - 后端 bug 必须加 pytest。
   - 前端状态 bug 至少加手工验收路径；能自动化则加 smoke。
   - 推荐质量问题必须加入 Eval quick 或新建真实问题集。

不允许：

- 只修用户点名的一个页面，放过同类页面。
- 只改 UI 文案，不修数据流。
- 只绕过缓存，不解释缓存策略。
- 只把错误结果藏起来，不改推荐排序根因。

---

### P0：马上修，影响核心体验

目标：先让用户测试不再明显翻车。

1. **推荐食材强约束**
   - 修 `app/services/decision.py`
   - 牛肉韭黄不得首推芹菜炒牛肉。
   - 加测试。

2. **菜谱搜索搜广推**

## 4. 给 subagent 的硬性要求

1. 不准只改 UI，不改数据逻辑。
2. 不准只改后端，不验证前端是否用上。
3. 每批必须给：
   - 修改文件。
   - 问题根因。
   - 修复策略。
   - 测试命令。
   - 手工验收步骤。
4. 推荐/搜索必须加回归测试。
5. 新用户数据隔离必须用两个账号实测。
6. 不能再写“全部完成”而没有真实用户路径验证。
7. 每修一个问题，必须补一段“同类问题排查结果”。
8. 每批修复后，必须把用户原始反馈逐条回归，不允许只跑单测就结束。
9. 如果发现计划外同类问题，必须记录到修复文档，不要偷偷顺手改完不说明。

## 5. 迭代回路

本轮以后按这个节奏推进：

```text
用户实测反馈
  -> 归类成缺陷族
  -> 定位根因层
  -> 修当前问题
  -> 扫同类页面/接口/状态
  -> 加测试或验收脚本
  -> 写复审文档
  -> 用户再测
```

每轮复审都要回答 5 个问题：

1. 这个问题为什么发生？
2. 同类地方还有没有？
3. 修复后有没有自动化测试或明确手工验收？
4. 有没有引入新的状态不一致？
5. 是否需要沉淀到 Eval 用例？

其中推荐、搜索、Agent 回复质量问题，必须沉淀到 Eval。  
其中用户隔离、收藏、用餐计划问题，必须沉淀到 API/DB 测试和手工验收路径。

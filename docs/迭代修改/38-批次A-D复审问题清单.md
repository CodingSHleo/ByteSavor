### P0-1 社区列表点赞按钮调用了不存在的 API 方法

代码证据：

- `bsapp/src/pages/community/community.vue`
  - `toggleLike()` 调用 `ApiService.likePost(post.id)`
  - `toggleLike()` 调用 `ApiService.unlikePost(post.id)`
- `bsapp/src/api/index.js`
  - 实际存在的是 `likeCommunityPost(postId)`
  - 实际存在的是 `unlikeCommunityPost(postId)`

根因：

后端点赞接口和 API service 已经实现，但社区列表页面接错方法名。H5 构建不会检查运行时对象方法是否存在，所以构建通过不能证明按钮可用。

用户影响：

社区列表点击“点赞”会进入 catch，显示“操作失败”，用户会认为点赞/取消赞没有修好。

修改要求：

1. 将社区列表调用改为：
   - `ApiService.likeCommunityPost(post.id)`
   - `ApiService.unlikeCommunityPost(post.id)`
2. 或者在 `ApiService` 里加兼容别名：
   - `likePost(postId) { return this.likeCommunityPost(postId) }`
   - `unlikePost(postId) { return this.unlikeCommunityPost(postId) }`
3. 推荐直接改页面调用，避免引入含糊别名。

检查方式：

1. 注册/登录用户 A。
2. 创建社区帖子。
3. 在社区列表点击“点赞”，按钮应变成“已赞”，计数 +1。
4. 再点一次，按钮应变成“点赞”，计数 -1。
5. 刷新社区列表后，`liked_by_me` 状态仍正确。

建议新增测试：

- 前端静态检查：禁止 `ApiService.likePost` / `ApiService.unlikePost` 再出现。
- 后端已有 `liked_by_me` 测试可保留。

### P0-2 菜谱库搜索“韭黄炒蛋”仍然匹配不到“韭黄炒鸡蛋”

代码证据：

- `bsapp/src/pages/explore/explore.vue`
  - `_tokenizeQuery('韭黄炒蛋')` 返回 `['韭黄炒蛋', '炒鸡蛋', '韭黄']`
  - `_searchRecipes()` 使用 `terms.every(t => searchText.includes(t))`

最小复现：

```js
terms = ['韭黄炒蛋', '炒鸡蛋', '韭黄']
searchText = '韭黄炒鸡蛋 韭黄 鸡蛋'
terms.every(t => searchText.includes(t)) // false
```

根因：

分词后仍保留原始整串 `韭黄炒蛋`，并且所有 token 必须命中。`韭黄炒鸡蛋` 不包含连续子串 `韭黄炒蛋`，所以依然失败。

用户影响：

用户已经明确实测“菜谱库里面有韭黄炒鸡蛋，我搜索韭黄炒蛋却匹配不上”。当前修复没有真正解决这个问题。

修改要求：

1. 搜索逻辑改为“核心 token AND + 同义词 OR”，不能把原始整句作为强制 token。
2. 对 `韭黄炒蛋` 应拆出：
   - 必须命中：`韭黄`
   - 可等价命中：`炒蛋` 或 `炒鸡蛋` 或 `鸡蛋`
3. 对 `番茄炒蛋` 应等价支持：
   - `番茄` / `西红柿`
   - `炒蛋` / `炒鸡蛋` / `鸡蛋`
4. 对 `牛肉韭黄` 应支持多 token，按命中数排序：双命中优先，单命中其次。
5. 这段逻辑不要只藏在 `.vue` 里，建议抽到 `bsapp/src/utils/recipe-search.js`，便于单元测试。

检查方式：

必须覆盖以下用例：

| 输入 | 数据中存在 | 期望 |
|------|------------|------|
| `韭黄炒蛋` | `韭黄炒鸡蛋` | 命中 |
| `番茄炒蛋` | `番茄炒蛋` / `番茄炒鸡蛋` | 命中 |
| `炒蛋` | 鸡蛋类菜谱 | 命中 |
| `牛肉韭黄` | 韭黄菜、牛肉菜 | 有结果，双命中优先 |

### P0-3 首页“刷新推荐/生成推荐”没有真正触发 refresh 语义

代码证据：

- `bsapp/src/pages/home/home.vue`
  - `generateRecommendations()` 始终调用 `ApiService.generateMealPlan(n)`
  - `refreshRecommendations()` 只是再次调用 `generateRecommendations()`
- `bsapp/src/api/index.js`
  - `generateMealPlan(ingredients)` 请求体没有 `refresh`
- `app/routers/decision.py`
  - `DecisionRequest.refresh` 只在未登录用户缓存分支中跳过 cache
  - 登录用户本来不走 cache，所以 `refresh=true` 也不会改变排序

根因：

后端只加了 `refresh` 字段和“跳过缓存”，但前端没有传；更关键的是，对登录用户或无缓存场景，跳过缓存不会改变结果。用户点击“刷新推荐”期望换一批，但当前算法是确定性排序，结果自然不变。

用户影响：

用户实测“生成推荐/刷新推荐内容根本没更新”仍然成立。

修改要求：

1. 前端：
   - `generateRecommendations({ refresh = false } = {})`
   - 普通加载 `refresh=false`
   - 点击“刷新/生成推荐”时传 `refresh=true`
   - `ApiService.generateMealPlan(ingredients, { refresh })` 把 `refresh` 写入请求体
2. 后端：
   - `refresh=true` 不能只跳过 cache，必须产生不同候选窗口。
   - 可选方案：
     - 按用户、ingredients、日期维护推荐游标；
     - 或请求体增加 `exclude_recipe_ids`，前端把当前 Top N 传回；
     - 或在同分/近分结果中做稳定轮换。
3. 不能牺牲质量：刷新后的结果仍必须满足食材覆盖、时间、偏好等硬要求。

检查方式：

1. 首页有同一批食材，例如 `牛肉、韭黄`。
2. 第一次推荐记录 Top 3 recipe_id。
3. 点击刷新。
4. 第二次结果至少 Top 1 或 Top 3 有变化。
5. 如果无更多可换结果，前端应明确提示“已展示最匹配结果”，不能静默不变。

建议新增测试：

- 后端 API 测试：同一 payload，`refresh=false` 与 `refresh=true` 在候选数足够时返回不同首屏。
- 前端静态测试：`refreshRecommendations()` 必须传 `refresh: true`。

### P0-4 推荐“牛肉韭黄”仍未形成硬约束闭环

代码证据：

- `app/services/decision.py`
  - `_rank()` 只排除 `coverage == 0`
  - 命中任意一个用户食材的菜谱仍会进入 candidates
  - 只靠分数让完整命中排前，并没有硬性禁止“只含牛肉”的菜进入 Top
- `app/seed/recipes.json`
  - 数据中明确存在：
    - `韭黄炒肉末`
    - `韭黄炒鸡蛋`
    - `韭黄炒肉丝`
    - `韭黄莴笋炒鸡蛋`
    - `芹菜炒牛肉`

根因：

批次 A 文档写“硬过滤排除无韭黄菜”，但代码实际上只排除“完全不命中用户食材”的菜。`芹菜炒牛肉` 命中 `牛肉`，所以不会被排除。

用户影响：

用户输入 `牛肉韭黄` 时，只含牛肉的菜仍可能进入推荐列表，尤其当韭黄菜谱被时间、目标、标签等条件影响时，体验仍会偏离。

修改要求：

1. 用户明确输入 2 个及以上食材时：
   - Top 1 必须优先使用更多用户食材。
   - 如果存在命中 `韭黄` 的菜，则 Top 不应是完全无韭黄菜。
2. 推荐分层：
   - 第一层：完整覆盖全部用户食材。
   - 第二层：覆盖稀缺/更具体食材，例如 `韭黄` 优先于泛化主料 `牛肉`。
   - 第三层：只覆盖部分食材，并必须显示“缺少/未使用 X”。
3. 对 `牛肉韭黄` 这类场景，应优先韭黄相关菜；没有牛肉+韭黄组合时，可以推荐 `韭黄炒肉丝` 或 `韭黄炒鸡蛋`，但不能首推 `芹菜炒牛肉`。
4. `_recommend_meta()` 当前把所有 scored 菜谱的食材汇总后挂到 `result[0]._meta`，这会导致首个菜谱的缺失说明不准确。应改成每个 recipe 自己生成 `matched_ingredients/missing_ingredients`。

检查方式：

```bash
curl -X POST http://127.0.0.1:8000/v1/decision/meal-plan \
  -H 'Content-Type: application/json' \
  -d '{"ingredients":["牛肉","韭黄"],"constraints":{"time_limit":30,"goal":"fat_loss"}}'
```

验收：

- Top 结果不得是 `芹菜炒牛肉`。
- Top 结果至少包含 `韭黄`，除非数据库完全没有韭黄菜谱。
- 每个结果都返回自身的 `matched_ingredients` 和 `missing_ingredients`。

### P1-5 新用户“有数据”问题还要区分后端数据和前端本地历史

代码证据：

- `bsapp/src/store/auth.js`
  - 登录切换时只清理：
    - `last_ingredients`
    - `agent_conversation_id`
    - `inventory_items`
    - `recognition_result`
- `bsapp/src/store/history.js`
  - 历史记录 key 是 `app_history_records`
  - 当前未在登录切换时清理
- `bsapp/src/pages/home/home.vue`
  - 还会写入 `plan_meal_slot`

根因：

v5 做了部分本地缓存清理，但没有完整梳理“用户私有 storage keys”。用户看到“新注册就有数据”可能来自：

- 后端 seed/默认社区公共数据；
- 用户私有库存/计划没有隔离；
- 前端本地历史记录、上次识别、推荐记录未清理；
- 退出登录后 store 内存未清空。

修改要求：

1. 定义统一用户私有 key 清单：
   - `last_ingredients`
   - `agent_conversation_id`
   - `recognition_result`
   - `inventory_items`
   - `app_history_records`
   - `plan_meal_slot`
   - 其他页面新增的用户私有缓存
2. `auth.setAuthData()` 和 `auth.clear()` 都调用同一个 `clearUserScopedStorage()`。
3. `historyStore` 在切换用户时同步清空内存 `items.value`，不能只删 storage。
4. 登录后首页必须以真实后端用户数据为准：
   - 新用户库存为空。
   - 今日用餐计划为空。
   - 私有历史为空。
   - 社区公共内容可以存在，但要标明这是公共社区内容，不是用户私有数据。

检查方式：

1. 用户 A 添加库存、生成推荐、添加计划、收藏内容。
2. 退出登录。
3. 用户 B 新注册登录。
4. 首页库存、今日计划、历史记录、识别缓存均为空。
5. 社区公共帖子可见，但收藏/点赞状态不继承 A。

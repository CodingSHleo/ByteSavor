# ByteSavor 迭代审查修改建议 v1

日期：2026-06-20  
审查对象：`docs/迭代修改/` 中 01-16 修改说明，以及当前未提交代码改动  
审查方式：阅读修改说明、对照关键代码、运行后端新增测试、运行前端 H5 构建  

## 0. 总体结论

这轮 subagent 的方向基本符合我们之前的方案：Hard Evaluator、phase、termination_reason、MemoryContext、纠错日志、图片缓存、前端 Agent 时间线都已经有实际代码落地。

但当前不能直接进入演示或合并，原因是存在一个硬阻塞和几个实现偏差：

1. **P0 阻塞：前端 H5 构建失败**，首页模板混入了中文弯引号。
2. **P1：MemoryContext 的会话记忆没有真正接到 `/v1/agent/execute` 入口**，`previous_state` 永远是 `None`。
3. **P1：普通 AgentRuntime 的最终 reply 可能被 evaluation issue 覆盖**，事件顺序和取 reply 逻辑不一致。
4. **P1：用户确认里的“重新推荐”会把助手回复再次发给 Agent，而不是原始用户请求。**
5. **P2：迭代文档和实际变更范围不一致，可见文档副本也少了 15、16 两篇。**

后端新增的 39 个 Agent 规范化测试在当前环境通过；包含 MySQL 的回归测试因沙箱无法连接 `127.0.0.1:3306` 失败，不能据此判断业务失败，但 README 中“48 个测试通过”的说法在当前环境无法复现，需要写清运行条件。

## 2. P1：MemoryContext 会话记忆没有真正接到 API 层

### 证据

`app/routers/agent.py:41-46`：

```python
memory_context = await build_memory_context(
    db, user_id or None,
    previous_state=None,
    goal=goal,
)
```

这里 `previous_state` 永远传 `None`。虽然 `LangGraphAgent.run()` 内部会从内存/Redis 恢复上一轮状态，但这个恢复发生在 runtime 内部，而 `memory_context` 已经在路由层提前构造完了。

### 影响

文档中说“MemoryContext 包含上一轮 ingredients / recipes / goal”，但 API 实际返回的 `memory_context.conversation_memory` 和 `memory_used` 不会体现上一轮会话。答辩时如果展示“沿用上一轮识别”，可能和真实返回不一致。

### 修改建议

选择一种实现，不要两边各做一半：

方案 A，推荐：把 MemoryContext 构造下沉到 runtime。

- `LangGraphAgent.run()` 先 `_load_previous_state(conversation_id)`。
- 然后把 `previous_state` 交给 `build_memory_context()`。
- 或者在 state 恢复后调用 `build_memory_used(state["memory_context"])` 并写回 `state["memory_used"]`。

方案 B，较小改动：给 `LangGraphAgent` 暴露只读方法。

- 新增 `async get_previous_state(conversation_id)`。
- `app/routers/agent.py` 在构造 `memory_context` 前先读取上一轮状态。
- 再传 `previous_state=previous`。

同时需要改返回逻辑：

```python
result["memory_context"] = result.get("memory_context") or memory_context
result["memory_used"] = result.get("memory_used") or build_memory_used(result["memory_context"])
```

不要永远用路由层初始 `memory_context` 覆盖 runtime 中更新后的上下文。

### 必补测试

新增或修改 `tests/test_agent_memory_context.py`：

1. 同一 `conversation_id` 第一轮推荐出 `牛肉、南瓜`。
2. 第二轮输入“把刚才的菜生成购物清单”。
3. 断言返回的 `memory_used` 包含 `conversation / last_ingredients` 或 `conversation / last_recipes`。

## 3. P1：普通 AgentRuntime 的 reply 可能被 evaluation issue 覆盖

### 证据

`app/agent/runtime.py:127-148` 中 `_finish_run()` 先 append `final`，再 append `evaluation`。

`app/agent/runtime.py:239-243` 中 `_result()` 取最后一个带 `message` 的 event：

```python
final_message = next(
    (event["message"] for event in reversed(state["events"]) if "message" in event),
    "",
)
```

evaluation 的 issue 内部含 `message`，虽然当前 event 顶层没有 `message`，短期未必触发；但这个逻辑很脆弱。只要后续 evaluation event 加顶层 `message`，reply 就会变成评估文案，而不是最终回复。

更重要的是：普通 runtime 的事件顺序是 `FINISHED -> EVALUATING`，而 LangGraph 是 `EVALUATING -> FINISHED`，两个 runtime 语义不一致。

### 影响

前端时间线、答辩口径和测试会出现不一致：我们希望 Loop 是 `ROUTING -> EXECUTING -> EVALUATING -> FINISHED`，普通 runtime 现在不是。

### 修改建议

统一两个 runtime 的事件顺序：

1. 先 `evaluate_hard(state)`。
2. append `evaluation` event。
3. 根据 evaluation 和 state errors 计算 status / termination_reason。
4. 再 append `final` event。
5. `_result()` 明确优先取 `type == "final"` 的 message：

```python
final_message = next(
    (event.get("message", "") for event in reversed(state["events"]) if event.get("type") == "final"),
    "",
)
```

### 必补测试

在 `tests/test_agent_loop_engineering.py` 增加：

- 普通 `AgentRuntime` 的 event types 中，`evaluation` 必须早于 `final`。
- `result["reply"]` 必须等于 final event 的 message，而不是 evaluation 内容。

## 4. P1：确认卡片的 retry 使用了助手回复，不是用户原请求

### 证据

`bsapp/src/pages/home/home.vue:746-750`：

```javascript
if (option.action === 'retry') {
  agentMessage.value = msg.text || ''
  sendAgentMessage()
}
```

这里传入的 `msg` 是 assistant 消息，`msg.text` 是 `r.reply`，不是用户原始输入。

### 影响

用户点击“换一批推荐/重新搜索”时，Agent 会收到类似“已找到 3 个菜谱...”的助手回复，而不是“牛肉南瓜减脂30分钟”。这会导致意图漂移，推荐质量不稳定。

### 修改建议

创建 assistant 消息时保存原始用户输入：

```javascript
agentMessages.value.push({
  id: msgId,
  role: 'assistant',
  text: r.reply || '我已完成分析，并整理了推荐食谱。',
  sourceText: m,
  result: { ...r, events: [], _fullEvents: r.events }
})
```

retry 时使用：

```javascript
agentMessage.value = msg.sourceText || agentMessages.value.findLast(x => x.role === 'user')?.text || ''
```

同时避免递归触发空请求。

## 5. P1：Hard Evaluator 会让所有成功推荐都变成 PARTIAL

### 证据

`app/agent/evaluator.py:92-102`：

```python
if recipes and verdict in ("PASS", "PARTIAL"):
    issues.append({"code": "NEEDS_USER_CONFIRMATION", ...})
    if verdict == "PASS":
        verdict = "PARTIAL"
```

### 影响

任何正常推荐都会被标记为 `PARTIAL`，前端会一直显示“部分通过/需要确认”。这符合“用户确认”的产品方向，但会削弱 Hard Evaluator 的语义：`PARTIAL` 不再代表“有风险”，而是代表“正常推荐也要确认”。

### 修改建议

把“软确认”从 `verdict` 中拆出去：

```python
EvaluationResult(
    verdict="PASS",
    issues=[],
    suggestions=[],
    confirmations=[...]
)
```

短期最小改动：

- 保持 `verdict == PASS`。
- 追加 `suggestions` 或单独 event 字段 `confirmation_required: true`。
- `_build_confirmation_prompts()` 根据 `confirmation_required` 或 recipes 生成确认卡片，不要污染 hard verdict。

### 验收

- 完全正常且核心食材覆盖的推荐，evaluation verdict 应为 `PASS`。
- 前端仍可以显示“是否喜欢/是否接受”的确认卡片。

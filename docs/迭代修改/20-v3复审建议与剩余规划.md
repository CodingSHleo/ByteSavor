## 2. v2 已经完成得比较好的部分

### 2.1 Hard Evaluator 主体修正有效

检查文件：`app/agent/evaluator.py`

已经完成：

### V3-4：纠错日志 fire-and-forget 需要开发期可观测

严重度：中  
涉及文件：

- `bsapp/src/pages/ingredient-recognition/ingredient-recognition.vue`

问题：

现在 edit/delete 调用：

```js
ApiService.recordCorrection(...).catch(() => {})
```

这对演示稳定是合理的：纠错日志写失败不应该打断用户修改。但长期风险是 correction memory 看起来接了，实际可能一直写失败，而且开发者完全不知道。

修改要求：

保留不阻塞用户，但开发环境至少打印错误：

```js
ApiService.recordCorrection(payload).catch((e) => {
  if (import.meta.env?.DEV) console.warn('recordCorrection failed', e)
})
```

如果当前 uni 构建环境不支持 `import.meta.env.DEV`，可以用项目已有的调试开关或简单 `console.warn`。不要弹 toast 打扰用户。

检查方式：

1. 后端停掉或 token 失效时，编辑识别项。
2. 页面仍能完成编辑。
3. 控制台能看到 correction 失败日志。

### 6.1 下一轮不要再优先扩业务功能

当前 Agent 规范化主体已经有了。下一轮如果继续加社区、清单、页面功能，会让系统更散。建议先做质量闭环。

推荐顺序：

1. 修正文档证据和同步问题。
2. 补 3-5 个关键接口级回归测试。
3. 做最小离线黑箱 Eval。
4. 再考虑 DeepSeek Judge。
5. 最后再做真 SSE/异步任务。

### 6.2 黑箱 Eval 的最小可落地版本

目标不是一步到位 50 条 + LLM Judge，而是先跑通闭环。

建议子 agent 下一轮实现：

```text
evals/
  cases/
    quick.jsonl
  reports/
  runner.py
  scorer.py
```

P0 要求：

- 10 条黄金用例。
- 每条包含完整 context、current_input、expected_checks。
- 可以直接调用 `LangGraphAgent` 或测试 ASGI `/v1/agent/execute`。
- 不调用真实 DeepSeek Judge。
- 使用确定性规则 scorer。
- 输出 JSON + Markdown 报告。
- 报告必须记录：
  - case_id
  - total_score
  - failed_checks
  - termination_reason
  - events 数量
  - memory_used
  - evaluation verdict

验收命令建议：

```bash
JWT_SECRET=test-review-secret /Users/liwenbin930/Desktop/bytesavor-backend/venv/bin/python evals/runner.py --quick
```

验收标准：

```text
生成 evals/reports/latest.json
生成 evals/reports/latest.md
quick set 至少 10 条全部跑完
总体分 >= 4.0 或明确列出失败原因
```

### 6.3 DeepSeek Judge / 双 Agent 评估的正确放置

双 Agent 评估不是不可行，也不是不值得做。当前建议是：

1. 先放在离线 Eval 里做 LLM Judge。
2. 用人工抽样校准 rubric。
3. Judge 输出稳定后，再考虑把一部分能力下放到运行时。

不要现在直接让运行时 DeepSeek Judge 决定是否重试或阻断推荐。原因：

- 会增加延迟。
- 会增加 API 成本。
- Judge 也可能幻觉。
- 演示时更容易因为外部 API 抖动出问题。

运行时可以先保持：

```text
Hard Evaluator 管事实硬规则
用户确认管主观偏好
离线 LLM Judge 管版本质量
```

后续如果要做运行时双 Agent，必须满足：

- 默认关闭，有配置开关。
- 超时 5-8 秒。
- 出错不影响主回复。
- 只评估软维度，如步骤清晰、口味合理、解释质量。
- 不能覆盖硬规则事实结论。
- 必须有测试证明 Judge fail-open，不会拖垮主链路。

### 6.4 SSE 的建议

当前前端 events 回放已经足够支撑答辩演示。真 SSE 不是当前最紧急项。

如果后续做，只建议新增一个接口，不要重构所有接口：

```text
POST /v1/agent/execute/stream
```

第一版只流式推送 Agent events：

```text
event: phase
data: {"type":"plan","phase":"ROUTING",...}

event: phase
data: {"type":"tool_start","phase":"EXECUTING",...}

event: final
data: {"reply":"...","recipes":[...]}
```

前端保留当前回放组件，只把数据来源从一次性数组改成 SSE 增量。

## 9. 最终判断

v2 的工程主体可以认可：Agent 已经从“能调工具”推进到了“有事件、有评估、有记忆、有前端可解释展示”的状态。

但 v2 还不是最终交付态。下一步最关键的不是继续加功能，而是让质量证据站得住：

- 测试结论必须可复现。
- 文档目录必须同步。
- 记忆和确认逻辑必须有接口级回归测试。
- 黑箱 Eval 要开始最小闭环。

完成这些后，再讨论 DeepSeek Judge / 双 Agent 软评估会更稳。这个 idea 值得保留，但应该先在离线 Eval 中验证，再进入运行时。
